Open source ·
GPU performance

LLM serving, measured fairly

Every engine comparison I found used a different model, GPU or memory setting, so none of them answered the question a platform team actually has: on our hardware, which engine serves more users? I built a harness that runs vLLM and SGLang (TensorRT-LLM supported) on the same GPU, model, prompts and memory budget, and times every streamed token from 1 to 64 concurrent users.

609 vs 384

tokens per second at 64 users, vLLM vs SGLang, same Tesla T4

The surprise was quantization. 4-bit AWQ made a single user 2.3x faster, but at 64 users it added only 5%. On this GPU it is a latency win, not a capacity win, which changes how you would size a fleet. Separately, my fused Triton kernels in llm-kernels reach 78% of the T4's peak memory bandwidth.

The call I made
Hold everything constant except the engine, or the numbers mean nothing. Same model, prompts and memory budget, and latency timed from the client side, token by token.
What it doesn't tell you yet
This is closed-loop load on one T4 with short prompts. The next round adds open-loop load and 8K context, where the ranking could change.

02

Production ·
Sidecoach Sports

An AI gateway and agents a youth sports company can trust

The company wanted LLM features and AI operations, under COPPA and FERPA, with no platform team. Every team needed its own access and spend limits, no student data could reach a model, and every agent action had to be traceable. I was the first platform hire, so this was mine to design.

Instead of model keys living in every app, there is one gateway in front of every LLM call: Entra ID sign-in, per-team keys and limits, PII redaction, and an OpenTelemetry trace for each request. Behind it sit an MCP agent service with RAG over internal content, and an SRE agent suite on Azure AI Foundry that triages alerts and opens Jira tickets.

Nothing touches production until an engineer says yes.

  1. Alert fires
  2. →
  3. Agent triages and summarizes
  4. →
  5. Engineer approves
  6. →
  7. Runbook runs
  8. →
  9. Jira ticket updated
The call I made
One gateway instead of keys in every app. It gives one place to redact PII, cap spend and trace calls, so adding a model or a team is a config change.
The trade-off
The approval step makes the agents slower than fully autonomous ones. For a company handling student data, that is the right trade, and the agents still do the triage and the writing.
