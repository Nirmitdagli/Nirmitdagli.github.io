vLLM vs SGLang on a T4: what 2,048 requests showed

vLLM served 609 tokens per second to SGLang's 384 at 64 users. And 4-bit quantization made single-user decode 2.3x faster, but barely helped at 64 users. Here's why both happened.

Every serving-engine comparison I found online used a different model, a different GPU, or a different memory setting for each engine, so the numbers couldn't be compared. I wanted one harness I could point at any OpenAI-compatible server and trust. So I built llm-serving-bench and ran it on the GPU anyone can get for free: a Colab Tesla T4.

The setup

  • Hardware: Tesla T4, 16 GB, about 320 GB/s of memory bandwidth.
  • Engines: vLLM 0.31.0 and SGLang 0.5.21, one at a time, each given the same 85% GPU memory budget.
  • Model: Qwen2.5-1.5B-Instruct, in fp16 and as its AWQ 4-bit version.
  • Load: closed-loop users at 1, 4, 16 and 64 concurrency. 128 requests per level, 512 input tokens, exactly 128 output tokens (ignore_eos), greedy decoding. Every run completed 128 of 128 requests: 2,048 in total.

Three choices keep it fair. Every prompt is random and unique, so neither engine's prefix cache can make it look faster. Output length is fixed, so both engines do exactly the same work. And 8 warm-up requests run before timing, so CUDA graph capture isn't counted. I measured time to first token (TTFT), time per output token (TPOT), total output tokens per second, and peak GPU memory.

For a single user, decode speed was identical: 20 ms per token on both. The difference was everywhere else. SGLang's first token took about 2x longer even at one user, and its throughput grew less as users were added. At 64 users, vLLM delivered 1.6x the throughput and its median user waited 1.8 seconds for the first token, against 7.4 seconds on SGLang.

Both engines ran Triton attention kernels on this GPU (vLLM picked TRITON_ATTN on its own; I started SGLang with --attention-backend triton). So the gap isn't the attention kernel. It's somewhere in scheduling, batching or the rest of the engine, and I haven't profiled it yet. I don't want to guess.

Result 2: continuous batching is the real multiplier

Going from 1 to 64 concurrent users raised vLLM's total throughput 12x, from 51 to 609 tokens per second. The cost is per-user speed: decode went from 20 to 92 ms per token. That trade is the core of serving capacity planning. One GPU can serve many more users at once if each of them accepts a slower stream.

Result 3: 4-bit helps one user a lot and many users a little

1vLLM5110619.96 ms8.51 ms

With one user, AWQ cut decode from 20.0 to 8.5 ms per token, 2.3x faster. At 64 users it added only 5% throughput (609 to 637). Same model, same GPU. Why?

Decode is memory-bandwidth bound. To produce each token, the GPU has to read every weight once. AWQ shrinks the weights from 3.03 GB to 1.11 GB, so with one user each step moves far fewer bytes, and the step gets faster almost in proportion.

With 64 users, the weights are still read once per step, but that one read is shared across the whole batch. What grows with the batch is attention and KV-cache traffic, and 4-bit weights don't shrink that. So the weight savings become a small slice of a much bigger step. Smaller weights do leave more room for KV cache: SGLang allocated 417K tokens of cache with AWQ against 346K with fp16.

The practical rule

Quantization is a latency tool for low-concurrency, interactive traffic. If you're throughput-bound at high concurrency, look at batching, KV-cache size and attention cost first.

Result 4: the kernel matters as much as the format

SGLang's AWQ run was slower than its own fp16 run on the T4: 35.7 against 20.1 ms per token for one user, while vLLM's AWQ run was 2.3x faster. Same checkpoint, same GPU. A 4-bit format only pays off if the engine has fast int4 kernels for that GPU architecture, and the T4 is an older one. "Use 4-bit" isn't a rule. You have to measure it on your hardware.

What this doesn't show

  • This is one older GPU and one small model. On an H100 with FlashInfer or FlashAttention, the ranking could change. SGLang in particular is tuned for newer hardware.
  • Load is closed-loop only. An open-loop (Poisson) mode would show queueing at a fixed request rate, which is closer to production traffic.
  • One input and output shape (512 in, 128 out). Long-context prefill stresses engines differently.
  • TensorRT-LLM is supported in the harness but not in these results: it runs from NVIDIA's container, which Colab can't start.
